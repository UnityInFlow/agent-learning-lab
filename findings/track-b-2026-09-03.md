## The two findings that matter more than the stop

Both are about the instrument. Neither crashed anything.

### 1. The run record is validated on the way out and truncated on the way in

`GET /api/runs/<id>` returns a four-key `runtime` block. `userSettingsIsolated`,
`shimsStripped` and `surface` are **absent — not null**. The API container is
`agent-observatory-observatory-api-1` in the **colima** docker context, built **2026-08-30**;
`V6__agent_surface.sql` merged after that. `run-agent.sh:850` sends all three on every run, and
obs#70's `validate-run-record.py`, live on the host, **accepts and asserts them** (a payload
carrying `userSettingsIsolated: true` exits 0).

**V6's surface recording is therefore L3 on the running instrument** while three project
documents describe it as done. A migration exists, a runner sends the values, a validator
checks them, and nothing persists them.

**What it cost this run:** `E-002`'s registered control assertion had to be amended before the
batch, in the open, because the field it named cannot be read. Evidence: the *AMENDED* block in
`experiments/E-002-isolation-contamination.md`.

### 2. The kept worktrees are hollowing out, and the scorer reports it as agent behaviour

`$TMPDIR` is `/var/folders/.../T/`, which macOS reaps — deleting **files** untouched for ~3
days and leaving the **directory tree**. Every `--keep` worktree lives there.

A complete worktree holds **17** `.kt` files. **Every scored B2 baseline run now holds 1 or 0.**
All still hold ~111 directories, so `RUNBOOK.md` §0.5 check #2 — `ls -d
${TMPDIR}observatory-run-<id>` — passes on every one of them.

The same scorer command that produced a six-attachment set for run `0a222393` on 2026-09-01 now

## The single thing most likely to overturn stop 8, added 2026-09-04

**That the nested path was never the right test, and the block is narrower than it looks.**
Everything above rests on `claude -p "/shipment-service-conventions"` answering `Unknown command`
for a nested skill. That proves the skill is **not in the slash-command registry at session
start**. It does *not* prove the skill can never enter the listing mid-run, and Claude Code
documents nested skills as becoming available *"when Claude reads or edits a file in a
subdirectory"* — which is a different mechanism from the registry the probe interrogated. Two
runs at that path recorded zero activations, but zero is also what a matched-but-not-selected
skill produces, and this design cannot tell those apart without a registration proof.

**If someone shows nested skills do enter the listing mid-run, stop 8's block is wrong** and the
lab could have run all along at `n = 5` per arm. The cheapest discriminator: one run at the
nested path whose *task* names the skill's marker explicitly, as the scratch-repo probe did. If
the marker comes back, the skill was reachable and the block dissolves into "the model did not
choose it" — which is the experiment, not a blocker.

## Why this halted at stop 6 — and what resuming found

**It halted here, was resumed later the same day, and stop 6 then closed.** The halt reasoning
is kept verbatim below rather than rewritten, because the interesting part is which half of it
survived contact. **Neither blocker materialised, and one of them was wrong when written.**

**§7, third condition: any proposed change to what the benchmark or evaluator measures.**

B3 is the first step that installs a treatment, and the itinerary's own pre-made decision
requires choosing where the customization overlay lives and wiring it through the runner's
`--customization` flag. Two things block that from being done unattended:

1. **`bench-critic`'s high finding is open and lands exactly here.** `findings/` is in neither
   `.gitignore` nor the evaluators' `IGNORE_RE`, so any file written into it by a push is
   collected by the scope guard as an untracked unrelated change and fails **AC6 with exit 21**
   — the harness blaming the agent for a file the hook wrote. B3 is the first step whose runs
   will be interleaved with pushes that write review findings. Resolving it means either
   changing what the evaluator counts as a scope violation, which is a registered variable, or
   diverging from this repo's practice of committing findings as evidence. **That is a decision
   about what the benchmark measures.**
2. **The instrument cannot currently record the thing B3 must prove.** B3's gate requires that
   the treatment reached the model and not the control — `instructionsHash` set on one arm and
   `null` on the other. That field survives, but the run record's *isolation* fields do not, and
   B3 runs both a treatment and a control whose difference is precisely a settings-and-memory
   channel. Registering a comparison on an instrument known to be truncating that class of
   field, one session after finding it, is how this project has produced six voided results.

Neither is a reason B3 is wrong. Both are decisions the itinerary did not pre-make and that
change what a version means, which §7's last condition reserves for the author.

### What stop 6 turned out to be worth

The step that looked blocked produced this run's clearest result, and it is a null:

**A 57-word instruction file, proved delivered by hash on every treated run and proved absent by
structure on every control, moved nothing.** Not the construct it targeted (2/10 vs 3/10), not
cost (−2.5 %), not duration (−11.4 %), not tool calls (Δ 0), not any rubric category. The
smallest p in the experiment is 0.165 and it points the wrong way.

Three things make the null worth something rather than an absence of result:

1. **The treated arm's own rate is refuted decisively, and the between-arm difference is not.**
   R1 predicted *"treatment reaches anchor 2 on ≥ 8 of 10"*. It reached **2 of 10**; if the true
   rate were 0.8, that has probability **0.000078**. That is a point claim about one arm and it
   needs no control. As a *difference* between arms it is a different story: the MDE table
   projected a control of 2/10 from B2's 1-of-5, **the control came in at 3/10**, and against the
   control that occurred the registered 8/10 gives **p = 0.070** rather than 0.023 — marginally
   outside the threshold. **The acceptance gate caught that, and the artifact originally claimed
   the stronger thing.** Both readings are now printed, the decision is unchanged, and
   `E-003` follow-up 6 is the fix: derive an MDE against the upper end of the baseline's
   interval, not its point estimate. Everything else — R2, prediction 4, DF1, DF2, DF3 — lands
   inside its MDE and is reported as **not detectable**, never refuted, which is E-002's
   follow-up 6 arriving as working practice.
2. **A second reader agreed with a first on all twenty runs, cell for cell.** The maintainability
   census was read off the source and committed *before* any scorer ran; the codex sheets
   afterwards name the same runs, with no disagreement in either direction.
3. **The dilution arm refused the obvious rescue.** The natural defence of R1 is that 57 words
   got lost in context. Burying the identical rules in 1 455 words made the construct **more**
   frequent (3/5 against 2/10), and no pair of the three arms separates. Pooled: 8 of 25,
   whatever the file says or whether one exists.

And the arm answered a question nobody registered: **a 25× larger always-on file costs +4.2 %.**
Three documents in these repositories argue for short instruction files, and the cost half of
that argument rests on a comparison that moved more than one variable. It cannot be made from
cost on this evidence.

**The gate's own removal clause was tested rather than trusted.** R3 was written into the file
predicted inert, so that *"remove every rule with no measured effect"* would have to remove
something or admit it cannot. It removed R3 — and then R1 and R2. `instructions-v0.1` is
**REJECTED and not replaced**: B3 asks for the smallest instruction file that changes measured
behaviour, and on this evidence that file is empty.
